# Подключение Supabase — для владельца проекта

Проект: `udrlbmlofdzevwvzssfw`, адрес `https://udrlbmlofdzevwvzssfw.supabase.co`.
В `web-source/cloud-config.js` находится только публичный publishable key. Service role, secret key и пароль PostgreSQL в приложении не используются.

## Однократная настройка

1. Открыть https://dfkzg.github.io/Temoraxis/setup/ . Скопировать SQL в Supabase → SQL Editor → New query и выполнить. Проверенный исходник: `supabase/schema.sql`.
2. В Results появится `invitation_code`. Сохранить его приватно и выдавать только участникам тестирования. В БД хранится SHA-256 кода; клиент не может его читать. Повторный запуск схемы не удаляет документы и не меняет код. Для смены кода выполнить в SQL Editor `select temoraxis_private.admin_invite_code(true);` — существующие участники сохранят доступ.
3. Authentication → URL Configuration: Site URL и разрешённый Redirect URL — `https://dfkzg.github.io/Temoraxis/app/planner.html`.
4. При включённом Confirm email требуется подтверждение адреса. Стандартная почта Supabase не предназначена для произвольных пользователей и ограничена адресами участников проекта; первый тест можно провести со своим адресом владельца. Для остальных пользователей настроить SMTP. Альтернатива для закрытого теста по приглашениям — выключить Confirm email; тогда владение email не проверяется. Это осознанная настройка владельца, приложение её не меняет.
5. На ПК открыть https://dfkzg.github.io/Temoraxis/app/planner.html . Настройки → Синхронизация → Облако Temoraxis. Создать аккаунт, подтвердить email (если требуется), войти с кодом приглашения. На Android установить версию 0.1.12+ и войти в тот же аккаунт. Код нужен только при первом подключении аккаунта, не каждого устройства.

Пароль приложения — отдельный пароль от пароля базы данных и учётной записи GitHub/Supabase. На новом устройстве с пустыми данными загружается копия облака; при разных локальных данных показывается выбор версии. Перед первой синхронизацией сохранить JSON-экспорт на телефоне и ПК.

## Защита данных

- Служебная таблица настроек в закрытой схеме также имеет RLS без клиентских политик; прямые права отозваны.
- Своё членство и документ видны пользователю по RLS. Другие пользователи и анонимные запросы не получают доступ к документам.
- Прямые INSERT/UPDATE/DELETE документов и членств запрещены клиентским ролям.
- `temoraxis_join` проверяет код; `temoraxis_push` получает пользователя только из auth.uid() и проверяет членство.
- Запись выполняется атомарно с ожидаемым номером версии. Устаревший запрос возвращает конфликт, а не перезаписывает новую версию.
- Обновление токена сохраняет идентичность аккаунта. Смена аккаунта во время запроса не позволяет применить ответ к другому аккаунту.
- Пароли и код приглашения не сохраняются в приложении. Токены сессии хранятся в локальном хранилище соответствующего браузера/WebView; запросы выполняются по HTTPS. Это не сквозное шифрование: владелец базы видит документы.
- Код SQL и публичный ключ можно публиковать. Код приглашения, пароли, access/refresh tokens, secret/service_role keys публиковать нельзя.

## Ограничения бесплатного сервиса

Supabase Free может приостановить неактивный проект; возобновляется в панели владельца. Для автоматических зашифрованных копий на Яндекс Диск или Google Диск подготовлен отдельный workflow; его нужно подключить по [инструкции владельца](BACKUPS.md). До настройки секретов и первого успешного запуска копии не создаются. JSON-копии на устройствах и локальная копия перед загрузкой из облака сохраняются.

Сохранённые изменения отправляются автоматически с задержкой около 1–2 секунд. При открытии/возврате и каждые 15 секунд открытое приложение проверяет изменения другого устройства. После восстановления интернета проверка возобновляется. Открытый черновик откладывает синхронизацию до закрытия редактора; конфликты требуют выбора версии. После правок на ПК открыть APK, чтобы обновились локальные будильники. Уже назначенным будильникам доступность облака не требуется. Фоновые push-уведомления для iPhone не реализованы.

## Проверки

`tests/test_supabase_sql.py` исполняет настоящую схему в отдельном PostgreSQL Docker-контейнере с имитацией ролей Supabase. Проверяет RLS, отсутствие прямых записей, приглашения, атомарные конфликты, валидацию и повторное применение схемы.

`tests/browser_supabase.cjs` проверяет настоящий клиентский транспорт с имитацией HTTP Supabase: две копии, конфликты, восстановление, повторения, удаления, смену аккаунта, обновление токена и подтверждение email. Настоящие Auth-сессии и синхронизацию в проекте владельца нужно проверить после выполнения SQL. Сам скрипт не создаёт пользователей в реальном проекте.

Другие источники: https://supabase.com/docs/guides/database/postgres/row-level-security ; https://supabase.com/docs/guides/api/api-keys ; https://supabase.com/docs/guides/auth/auth-smtp . Наш транспорт обращается к HTTP API напрямую; Supabase SDK в APK не добавлен.

SQL Editor может предупредить о destructive operations из-за DROP POLICY IF EXISTS: удаляются и пересоздаются только две именованные политики Temoraxis, а не таблицы или строки. RLS включается явно для всех трёх таблиц в скрипте.
